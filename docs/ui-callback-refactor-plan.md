# UI 回调化重构：第二阶段

## 1. 状态与目标

第一阶段已在 `6aa9417` 完成，文件组织见 [第一阶段方案](ui-file-organization-plan.md)。用户现已授权第二阶段实现；实施分支为 `refactor/ui-callbacks`，基线为 `67af525`。本轮完成按钮点击回调化，不改变控件更新/绘制调度，也不将文本编辑等协议一并回调化。

此前按源码基线 `67e5bad` 记录方案；下文明确本轮接口、迁移边界及验证结果。当前调度边界见 [应用层 UI 调用边界](app-ui-boundary.md)。

目标是减少仅为响应一次点击而存在的小型派生类型，让读者在面板组装处看清“创建什么控件、如何布局、触发什么行为”，而不是为理解一个按钮跳转多个文件。

核心方向：简单交互由通用控件接收回调实现；具有独立状态、绘制或交互协议的控件仍可使用继承。不是取消全部继承，也不是将 C++ UI 改造成浏览器或 JavaScript 框架。

## 2. 迁移前实现与目标分工

以下源码路径相对 `Rigid2DSimulation/`。迁移前 `framework/control/Button.h` 中的 `Button` 通过虚函数 `OnClick(App&)` 接收点击。应用层派生按钮覆盖该函数，并访问 `SimulationApp` 完成操作。

例如 `current/ui/bodyPanel/BodyButtons.cpp` 中：

- `BodyScriptApplicationButton` 将当前选中刚体的临时脚本写回，再调用 `simulationApp.scriptRuntime.RefreshBodyScript(selectedBody)`。编译和执行由脚本运行时负责，不由 Body 自己解析脚本。
- `BodyDeletionButton` 调用 `simulationApp.editor.RequestBodyDeletion(simulationApp.physicsWorld)`；选择处理交给 Editor，物体及关联连接的删除标记交给 PhysicsWorld，实际清理由后续帧完成。回调不应绕过这些入口自行操作容器。

回调化后的目标分工：

| 位置 | 职责 | 不应承担的内容 |
| --- | --- | --- |
| 框架通用控件 | 输入判定、显示、控件状态、在既定时机触发回调 | 刚体删除、脚本执行等模拟器业务 |
| Panel | 控件组装、布局、事件绑定、组织编辑交互 | 堆积所有场景和物理规则 |
| 应用或场景操作 | 执行具体业务，维护相关状态约束 | 依赖某个按钮的绘制或鼠标判定 |
| 专用控件 | 封装确有必要的编辑、列表或复合交互状态 | 仅为几行点击行为增加一个类型 |

这里的业务分工是设计方向，不授权同时重构 `SimulationApp` 或物理模块。若试点必须新增业务接口，先确定接口及范围；不能借回调化顺手做场景架构重写。

## 3. 已确认的约束

- 简单按钮优先使用回调组合，不再为每个行为建立一个派生按钮类型。
- 保留仍有实际职责的专用控件，例如连接列表、参数行和编辑器；逐个判断，不机械消除全部类型。
- 不引入事件总线、完整 MVC/MVVM、大量模板或每个按钮一个控制器。
- 不把原按钮逻辑全部搬进一个巨大的 Panel 构造函数；短绑定就地表达，较长处理根据职责确定归属。
- `struct` 改成 `class` 不是本阶段目标。确需封装时明确设计公开接口和私有状态，而不是批量替换关键字。
- 完成某个按钮替换后移除对应旧类型，不保留兼容别名或转发实现。若 `BodyButtons` 等文件组变空，删除并同步工程文件，不为维持目录外观保留空壳。
- 保持本地化键、DSL、存储格式、物理计算以及原有业务行为不变。不夹带正确性修复。
- C++ 文件保持 UTF-8 BOM、CRLF、4 空格缩进；函数 PascalCase，变量 lower camel，遵循现有长期代码风格规范及已确认的编码要求。

## 4. 本轮接口与生命周期

1. Button 持有 `std::function<void(App&)> onClick`。允许为空，绑定时不执行；沿用原框架提供的 App 引用，避免所有按钮都长期捕获应用对象。框架不认识 SimulationApp，业务绑定仍在应用层转换类型。
2. Button::Update 在原 OnClick 调用位置同步调用非空回调一次。删除旧虚函数和全部覆盖实现，不留双通道或兼容转发。chosen 更新、禁用判定、松开时触发和随后的 Render 均不改。
3. Body/Connection 回调无捕获，在点击时读取当前选择；保存加载读取当前面板路径。参数行只按值捕获行 id，创建按钮只按值捕获工具 mode，不持有场景对象或 shared_ptr，也不产生所有权环。
4. 创建面板的局部 addToolButton 仅在构造期间使用，不保留其 this 捕获。ShowFloatPanelButton 保留原有面板指针及逐帧文字/禁用同步，自己的点击回调捕获 this；该类型禁止按值复制，且不提供移动操作，菜单以 shared_ptr 稳定持有，不在析构时触发回调。目标面板由 UserInterface 持有，菜单使用期间不会被替换。
5. 参数删除仍按当前行索引标记，不改列表复用和延迟清理规则；不因本轮重构修复列表或索引的既有问题。
6. `Sync`、`Upload`、`OnDone`、`Discard` 及容器更新流程保持原样。四个动态文字按钮保留 Update，文字仍在点击前同步；不增加泛化的 onUpdate 回调或提前统一刷新全部菜单。

上述边界只适用于当前同步、单线程 UI。将来若允许控件复制、回调异步执行或替换面板，需要重新审查引用有效期，不能直接沿用这些捕获方式。

## 5. 建议执行顺序

### 5.1 建立行为基线

阅读控件事件流程及所有权链，记录点击触发、禁用状态、选择切换、销毁和焦点释放行为。构建当前版本，建立可重复的验证方式；能隔离的交互添加行为测试，不能自动化的明确记录人工步骤。

### 5.2 以 BodyPanel 的简单按钮试点

确认第 4 节中与点击有关的设计后，为通用按钮提供最小回调能力，并迁移应用脚本、删除刚体两个按钮。让 `BodyPanel` 的组装代码直接体现事件绑定。

保留 `BodyControls` 中仍有独立职责的编辑器、连接行和列表。本次不以“消灭整个文件”为目标。

### 5.3 按交互协议推广

试点验证通过后，盘点其余按钮的点击、每帧同步及显示逻辑，按行为相近的一组推进。不能只看 `OnClick` 就删除还覆盖 `Update` 的派生类型。

编辑器、选择框、参数行与列表单独评估；没有明确可读性收益时保留现状。无需预先规定每个控件一个提交，也不承诺强行回调化全部控件。

文档中的具体设计、对应代码和验证结果应在同一实施提交中落地，使用 `refactor(ui):` 等 Conventional Commit；不单独提交尚未实施的完成声明。

## 6. 验证与完成标准

| 验证对象 | 必须保持的行为 |
| --- | --- |
| 基础点击 | 按下、释放、禁用等条件下的触发时机及次数与原实现一致；绑定时不执行业务 |
| 刚体脚本 | 使用点击时的当前目标与临时脚本，保持运行时刷新入口、调用次数及错误传播方式 |
| 刚体删除 | 继续使用 Editor/World 删除入口，保持选择清理、关联连接标记、场景变化标记和延迟清理时机 |
| 选择与生命周期 | 切换选择、关闭面板、删除对象后，不因新增捕获产生悬空引用 |
| 显示与输入 | 本地化、按钮状态、焦点、输入占用及各更新阶段的顺序不变 |
| 后续迁移对象 | 保存加载、模式切换、参数增删等先记录各自基线，再验证，不能用按钮试点结果替代 |

- 每批执行 `Debug|x64` 构建及相应行为验证，检查引用和工程文件没有遗漏。
- 没有旧按钮与新回调双重执行，没有仅为兼容旧类型而保留的代码。
- 面板组装和事件绑定可直接阅读，复杂业务没有借机全部堆入面板。
- 更新本文件的实际迁移范围、保留类型及原因、验证结果；未验证的项目明确注明，不能宣称全部完成。
