# 风格迁移设计协议

## 1. 目的

本协议约束 `docs/code-style.md` 的存量迁移实施方式。任何模块在修改 C++ 代码前，必须先有对应的模块设计文档；代码改动、设计文档和 `docs/style-migration-status.md` 的状态更新必须进入同一个提交。

本文是长期执行规则，不是可单独提交的过程记录。

## 2. 可实施设计的最低条件

一个模块设计只有同时满足以下条件才可开始改代码：

- 精确列出本批所有非豁免旧名称、唯一目标名称和源码范围。
- 逐项说明不改的短名称及理由；数学公式局部量、外部 API、DSL 语法和二进制字段顺序必须显式豁免。
- 按命名主题而非机械按文件拆分提交；同一主题可以覆盖多个直接调用点。
- 明确每个提交不得触及的类型、字段或逻辑，避免全局替换。
- 给出旧名检索范围、`Debug|x64` 构建、GBK/CRLF 与 `git diff --check` 的验收要求。

未列入名称对照表的标识符视为“不改”，不得在实施时顺手迁移。

## 3. 文档与提交关系

- 新建或首次完善的模块设计文档，不单独提交；它与该模块第一个对应代码提交一起进入版本库。
- 后续代码提交必须同步勾选该模块设计文档的完成项，并更新 `docs/style-migration-status.md`。
- 纯排版提交可以引用已有设计文档，但不得夹带未列出的改名。
- 一个文档涉及多个命名主题时，首次代码提交提交文档全文；后续提交只更新状态。文档中的其他主题在其完成前保持未完成状态。

## 4. 模块划分

后续工作按以下独立边界设计和实施：

| 模块 | 设计文档入口 | 允许覆盖的直接调用链 |
| --- | --- | --- |
| `framework/basic` | `docs/remaining-module-style-design.md` 的基础数据段 | 数学与矩形类型的项目内调用点 |
| `framework/app` | 同上应用框架段 | 应用壳层及其直接调用点 |
| `framework/draw` | 同上绘制段 | 绘制函数、私有算法和直接调用点 |
| `framework/media` | 同上媒体段 | 字体、图块、音频及直接调用点 |
| `framework/parse` | 同上解析段 | 解析器内部；DSL 名称仍同时遵守 `docs/dsl-naming-migration.md` |
| `framework/control` | `docs/control-geometry-migration-plan.md` | 控件及 `current/ui` 的直接控件访问 |
| `current/common` | `docs/remaining-module-style-design.md` 的模拟应用段 | 场景、背景、参数和应用调度 |
| `current/rigid` | 同上刚体段 | 刚体、碰撞、创建器和场景构建函数 |
| `current/ui` | 同上 UI 段 | 面板装配及其直接控件访问 |

跨模块改名只有在名称属于同一公开接口或直接调用链时才允许；否则拆成后续模块提交。

## 5. 统一验收

每个代码提交均须在改动前、后执行 `Debug|x64` 构建；确认 C++ 保持 GBK 和 CRLF；按本批旧名限定检索范围；最后执行 `git diff --check`。不修改物理计算、条件、循环边界、求值次数、资源生命周期、调用顺序、DSL 语法或 `.rigid2d` 二进制布局。
