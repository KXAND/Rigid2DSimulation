# 代码风格规范

## 1. 地位与适用范围

本文是本项目唯一的长期代码风格规范。新代码必须立即遵守；存量代码按 `docs/naming-and-macro-refactor-plan.md` 分模块迁移，最终全库达标。

规则优先级如下：

1. 外部平台、编译器、第三方库的接口约束。
2. 本文。
3. 迁移计划中的执行顺序和验证要求。
4. 单个文件的局部说明。

项目自定义 DSL 不是外部接口。其函数名、配置键、作用域键与示例脚本应随 C++ 代码一起迁移，不保留旧名称兼容，也不改变脚本语法。`.rigid2d` 使用二进制顺序读写，没有可改名的字段；迁移期间不得改变其写入顺序、类型、长度表示或二进制布局。

## 2. 文件与编码

- C++ 源文件、头文件使用 GBK 编码和 CRLF 换行。
- 不进行批量转码；编辑后必须保持原文件的编码和 CRLF。
- 文件名使用 PascalCase，并与主要类型或明确职责一致，例如 `SimulationApp.cpp`、`SceneParameter.h`、`ShapeBuiltins.cpp`。
- 文件重命名必须同步更新 `#include` 和项目文件引用。

## 3. 命名

| 对象 | 规则 | 示例 |
| --- | --- | --- |
| 文件、类、结构体、枚举、类型别名 | PascalCase | `SimulationApp`、`ShapeBuiltins.cpp` |
| C++ 函数、项目 DSL 可调用函数 | PascalCase | `UpdatePosition`、`CreateBody` |
| 变量、成员、参数、项目 DSL 变量和配置键 | lower camel | `selectedBody`、`energyMultiplier` |
| 命名空间或类作用域的具名常量 | `kPascalCase` | `kPi`、`Color::kRed` |

- 函数内普通 `const` 变量仍使用 lower camel。
- 允许上下文清晰的数学或通用缩写：`x`、`y`、`dx`、`dy`、`id`、`ui`、`rgb`、`size`、`cnt`。
- 容器或文本长度在无歧义时使用 `size`；需要区分对象时使用 `<对象>Len`。
- `config` 是允许的工程常用缩写；需要限定领域时使用 `<对象>Config`，例如 `bodyConfig`、`shapeConfigs`。不使用 `cfg`。
- 当前值使用完整单词 `current`；长度使用 `Len` 后缀，例如 `currentLen`，不使用 `currLen`。
- 禁止项目内部含义不明的缩写、成员前缀和类型前缀，例如 `bo`、`mbs`、`_shs`、`m_`。
- C 标准库、Windows SDK 和第三方库的类型、函数、宏名称必须保持其外部接口拼写，例如 `FILE`、`fread`、`fwrite`。

## 4. 排版与控制流

- 使用 4 个空格缩进，禁止使用 Tab 缩进。
- 使用 Allman 大括号风格。
- 每条独立语句单独占一行；禁止在同一行书写多个独立语句。
- 所有 `if`、`else`、`for`、`while`、`switch` 等控制流主体必须使用大括号，即使主体只有一条语句。
- 相邻逻辑阶段之间空一行。空行用于分组，不代替必要的注释。
- 类型限定符使用 east-const：`Type const& value`、`Type* pointer`、`Type& reference`。

## 5. 包含与注释

`.cpp` 文件的包含顺序如下：

1. 对应的自身头文件。
2. C/C++ 标准库头文件。
3. 第三方或平台头文件。
4. 其他项目头文件。

同一组内按路径排序。必须在平台头之前定义的配置宏是例外，必须保留在对应平台头之前。

- 头文件必须直接包含其使用的完整类型声明所需的头文件，不依赖传递包含。
- 注释使用中文，说明原因、约束或非显而易见的影响，不复述代码表面行为。
- 保留有价值的历史注释；不做无意义的全量改写。

## 6. 宏

- 除平台、编译器或第三方 API 强制要求外，项目源码禁止定义宏。
- 必要宏使用全大写，作用域最小化，并在可行时紧邻 `#undef`。
- 禁止别名宏、函数宏、控制流宏、类型别名宏、标准库别名宏和上下文缩写宏。
- 使用显式变量、普通函数或局部私有函数表达意图；不以模板函数替换仅为隐藏缩写而存在的宏。
- 原有序列化宏必须逐调用点展开，不保留宏或模板封装。展开后使用 `file`、`size`、`<对象>Len` 或 `cnt` 等清晰局部名称，并保持原有二进制布局和执行顺序。
- 绘制算法宏必须改为同文件匿名命名空间中的普通私有函数；不得移入通用工具层。

## 7. 风格迁移边界

- 不保留旧 C++ 名称或旧 DSL 名称的 wrapper、别名或兼容层。
- DSL 迁移必须在所有 C++ 注册点、读取点、项目脚本和示例场景中同步完成。
- 除经确认的局部私有函数提取外，不以风格整理为名进行文件、类或大规模函数拆分。
- 不改变物理计算、条件、循环边界、求值次数、资源生命周期、调用顺序或脚本语法。
- 不以风格整理为名修复正确性问题；二进制序列化的可靠性改进应在独立分支处理。

## 8. 审查清单

- 文件、类型、函数、变量和项目 DSL 名称是否符合本规范。
- 是否引入了新的项目宏、隐式上下文或含义不明的缩写。
- 是否保持 GBK 与 CRLF，且没有无关格式化或转码差异。
- 是否将独立语句、控制流和逻辑块按本规范排版。
- DSL 改名是否同步更新全部项目内引用，二进制布局是否保持不变。
- 每个迁移提交是否独立构建通过，并使用 conventional commit。
